# Concrete VM clone preferences

Reviewed scenarios can select a destination storage pool for each source VM.
Replication carries that choice to every literal VM. A blank selection inherits
the template's disk pools; it does not inherit a previously processed VM's pool.
The setting applies to new full clones, not disk migration on existing guests.

The version 3 VM manifest declares `guest_preferences_version: 1` and an explicit
`storage` string or `null` on every VM. Pool names are bounded identifiers. Older
manifests without this marker keep their existing behavior and generated bytes;
opening and saving Scenario review explicitly opts into the new contract.

For a full attempt, the backend derives `r42_guest_storage` from the validated
manifest. Ansible extra vars select `proxmox_dest_vm_storage_name` by the current
literal VMID. This precedence prevents vault or imported playbook variables from
silently replacing the reviewed destination. `null` renders Ansible's `omit`, so
the clone request has no storage key. Configure and teardown do not apply this
clone preference. No credentials or allocation owner proofs belong in this map.

Preflight checks a selected pool's visibility, active/enabled state, VM image
support, available bytes and the token's `Datastore.AllocateSpace` privilege on
that exact pool. A present privilege with a false propagation flag still grants
the exact path. Unknown template disk sizes or insufficient selected-pool space
block deployment. Estimates are point-in-time checks, not storage reservations;
thin provisioning and concurrent allocation can change actual free space.
Legacy inherited-pool estimates retain their advisory behavior.

Requested disk sizes use the existing disk-growth contract. Preflight refuses
shrink requests, missing disks, CD-ROM targets and unreadable sizes/configuration.
It does not create extra disks or claim shrink/migration support.

The local regression consumer templates the actual clone body from controller
`99fd63c` (used by playbooks `a150867`) through Ansible, without running its HTTP
task. Mixed selected/inherited destinations remain exact despite conflicting
vault and import variables. Set `R42_PREFERENCE_CLONE_TASK` to that archived
`vm_clone.yaml` when running `tests/core/test_scenario_preferences.py` to include
this opt-in pinned-body check. Ordinary tests also cover the same omission and
precedence contract with a minimal harmless local playbook. No controller or
playbook source change is required.

## Reviewed cloud-init preferences

New Scenario reviews use `guest_preferences_version: 2`. This adds an explicit
`cloud_init` object to every literal VM, alongside the version 1 storage field:
`ssh_user`, `dns_servers` (one to three IPv4 strings or `null`) and
`dns_search_domain` (a bounded DNS domain or `null`). The SSH user must match the
guest's literal `ansible_user` in `hosts.yml`; disagreement refuses all resolve
scopes. Unknown cloud-init fields, including passwords and SSH keys, are refused.

The new form preserves the existing `1.1.1.1` DNS default. Clearing its DNS or
domain field deliberately omits that controller argument, retaining template
configuration. Existing saved fields remain authoritative over canvas defaults.
Older generated snapshots and version 1 storage-only manifests keep their bytes
until a user reviews the Scenario again. Save/reopen preserves the reviewed
preferences and their replication fan-out.

For full attempts, a validated `r42_guest_cloud_init` map protects both bootstrap
aliases and controller parameters at Ansible extra-vars precedence. A vault's
`default_admin_vm_ci_user` or `vm_ci_dns_ips` cannot silently change the selected
user or DNS. Passwords and SSH keys retain the private backend workspace contract;
the public map never carries them. This applies when bootstrapping new clones,
not a configure-only update of existing cloud-init state.

`R42_PREFERENCE_CLOUDINIT_TASK` enables the matching actual-controller-body local
consumer in `test_scenario_preferences.py`. It templates the pinned PUT body as
a harmless local module argument, proving per-VM user/DNS values and true omitted
keys despite conflicting vault/import values. It makes no Proxmox call and does
not claim guest image cloud-init support beyond that pinned runtime contract.
